# Modern Warfare 3: bring-up

This tree is a fork of [mw2-recompiled](https://github.com/PaulCombal/mw2-recompiled),
which runs Modern Warfare 2 (2009) natively on PC. The goal here is the same
for Modern Warfare 3 (2011), and later a PS4 build on top of it
(see [PS4](#ps4)). Nothing below has been run against an MW3 executable yet:
every address, every "should" and every estimate is to be checked.

Scope: **the campaign, offline.** The multiplayer needs the online services,
and Special Ops comes after the campaign boots.

## What carries over, what does not

MW3's engine (IW5) descends from MW2's (IW4), and both link D3D9, XAudio2 and
the C runtime statically ([runtime.md](runtime.md)). So the *runtime* (guest
memory, threads, kernel and XAM stubs, the Vulkan side, audio) should carry
over largely unchanged, and what is MW3-specific is:

| piece | where | how it is found for MW3 |
|---|---|---|
| the recompiler config: save/restore helpers, `setjmp`/`longjmp`, functions the analyser splits wrongly | `config/MW3.toml.in` | `tools/port_hooks.py`, then by hand |
| the jump tables | generated by XenonAnalyse | the `build.sh` step, as for MW2 |
| the hooked functions and globals | `runtime/title.h` | `tools/port_hooks.py` for code; data by hand |
| the MW2 fixes: network hardening, party and map-list patches, the multiplayer's engine fixes | `runtime/*.cpp` | **dropped** until the campaign boots; most are multiplayer-only |
| the title update | `build.sh`, `tools/xexpatch.cpp` | unknown: see [Title update](#title-update) |

## Steps

Each step ends with a check. Do not start the next until it holds.

### 0. Inputs

From your own disc: `default.xex` (and `default_mp.xex`, kept for later) and
the game files. Keep them under `mw3/`, which `.gitignore` excludes along with
`*.xex` and `*.pe`; never commit anything from the disc.

    mw3/tu0/default.xex      the disc's executable
    mw3/game/                .ff, .pak, .bik, ... from the disc

Check: `python3 tools/xexinfo.py mw3/tu0/default.xex` prints a header, and the
SHA-256 of the file is written down in your notes. The runtime refuses any
other executable than the one it was built for, so every later step is for this
exact file.

### 1. A flat image

    python3 tools/xexdump.py mw3/tu0/default.xex mw3/tu0/default.pe

Check: the file exists and `python3 tools/port_hooks.py --selftest` passes.

### 2. Find MW2's hooks in MW3

You need MW2's flat image (`mw2/default.pe`) for this; the tool compares the two.

    python3 tools/port_hooks.py --src mw2/default.pe --dst mw3/tu0/default.pe \
        --emit mw3_candidates.h

Read the report: `found` and `verify` are candidates, `ambiguous` and
`unresolved` need hand work (strings: `tools/strings_in.py`; callers:
`tools/xref.py`). Expect the D3D9, XAudio2 and C runtime functions to match
(libraries) and the engine functions (`Com_Error`, `Dvar_*`, `R_*`) to match
less, since the game's own code changed between the two titles.

Check: the save/restore helpers and `setjmp`/`longjmp` are each found once.
These go into the recompiler config and a wrong one miscompiles the whole game
quietly.

### 3. Recompile

1. Copy `config/MW3.toml.in` to `config/MW3.toml` and fill in the addresses.
2. Teach `build.sh` and `tools/title.py` an `mw3` title (the MW2 `sp`/`mp` and
   `tu6`/`tu0` machinery is the pattern; MW3 has one executable to start with).
   `tools/title.py` has it (`MW2_TITLE=mw3`); `build.sh` does not yet, and
   `tools/recomp_mw3.sh` stands in for it.
3. Run XenonAnalyse for the switch tables, then XenonRecomp, as `build.sh` does
   for MW2.

Expect the first run to need `functions = [...]` entries for leaf functions the
analyser ends early, as in `config/MW2.tu0.toml` (`tools/fixbounds.py` derives
the extents). Expect to find the `setjmp` caller loops by reading.

Check: the recompiled tree is generated and compiles.

### 4. Boot on the desktop

A new `title.h` block for MW3 names the hooks that turned out right. The first
runs are with almost every hook compiled out: the engine only has to get to
its first frame.

Likely first failures, in the order MW2's bring-up hit them
([runtime.md](runtime.md)):
- a thread-id or processor-number check that deadlocks (`r13`, KPCR);
- a memory allocation that wants a different alignment or size than MW2's;
- an import with no implementation, which `gen_kernel_stubs.py` stubs to 0 and
  the end-of-run report lists: implement the ones the game spins on;
- the D3D9 seam: the ring buffer and flip handshake ([d3d9-seam.md](d3d9-seam.md)).

Check: the main menu draws and the campaign's first level loads.

### 5. Playable on the desktop

Audio, input, saves. Movies are not supported by the MW2 recompilation either
(its README lists cutscene and loading movies as unsupported), so expect the same.
Check: the first mission plays through at a stable frame rate. **This is the
point to decide whether a PS4 build is worth starting**, from the measured
per-frame cost, not from a guess.

## Progress

Steps 0 to 3 have been run once, on one executable. `tools/recomp_mw3.sh`
repeats steps 1 and 3 from `mw3/tu0/default.xex` in about 15 seconds.

- **Executable:** `iw5sp_ship.exe`, title id `0x415608CB`, XEX version `0x16`,
  SHA-256 `d90bc8d93b7b8f6001ead8330271196a6ef7a5c2e4a9e9b63118f47d58a05912`.
  Image base `0x82000000`, entry `0x82459E58`, `.text` at `0x82090000`
  (`0x4566BC` bytes). Whether this is the disc's own build or an updated one is
  still open (see [Title update](#title-update)).
- **Step 2, hooks:** the MW2 image the hook addresses are taken from has to be
  the one `runtime/title.h` has a block for. A `default.xex` from the disc is the
  `tu0` layout, where many functions start eight bytes before the update's, so
  run `tools/port_hooks.py --version tu0`. Without it every address is eight
  bytes off and most hooks come back unresolved. With it, all 10 recompiler
  helpers are found once each; their bytes equal MW2's, except `setjmp` and
  `longjmp`, which differ only in linker-filled immediates and branch targets.
  The engine functions, MW2's disc address and MW3's (each a function start in
  both images and in the generated function map):

  | Hook | MW2 | MW3 | Found by |
  |---|---|---|---|
  | `T_D3D_Present` | `820C3390` | `820A16E8` | The one caller of `VdSwap` in each image, with the same chain of calls and imports (1988 and 1972 bytes) |
  | `T_D3D_ArenaWait` | `820B9800` | `8209B5E8` | Instruction signature |
  | `T_D3D_InitPixelShader` | `820B8B58` | `820984F0` | Instruction signature |
  | `T_Com_Error` | `822830E8` | `8229D688` | Same structure: error-depth counter, code 7 check, 4096-byte `vsnprintf` buffer |
  | `T_Cbuf_AddText` | `8227CF18` | `8228CA48` | Signature, reported as "verify" |
  | `T_Memcard_InitializeSystem` | `8230DF88` | `8232EC08` | Instruction signature |
  | `T_Image_FlushMove` | `823A52F8` | `823D4398` | Instruction signature |
  | `T_CG_CullZoom` | `8210FF80` | `821067A8` | Instruction signature |

  Also located, though the disc block does not hook them: `R_VideoSizes`
  `8238E5D0` -> `823D7320` and `R_SetVidConfig` `8238DDC8` -> `823D6B00`.

  Not found: `T_D3D_ReplayRecording`, `T_D3D_PatchVertexFetches`,
  `T_Job_WaitPredicate`, `T_CG_ViewFov`, `T_Dvar_RegisterInt`, and
  `T_DB_MissingAsset`, whose two strings MW3's ship build no longer has. MW2's
  `Com_Printf` and the print functions beside it have no counterpart: MW3 has
  no function with their shape (a varargs spill and a 4 KB frame), so printing
  looks to be compiled out of the ship build. The 8 `T_DATA_*` globals are by hand.
  D3D's device structure moved: the field `D3D_ArenaWait` reads at `[r3+10896]`
  in MW2 is at `[r3+11024]` in MW3, and `21628` is `21908`, so offsets the
  runtime reads from it must be found again, not carried over.
- **Step 3, recompile:** XenonAnalyse finds 128 jump tables. The first run gave
  377 "switch case outside function" lines at 27 sites; `tools/fixbounds.py`
  (`MW2_TITLE=mw3`) derived 26 leaf-function extents for `config/MW3.toml`, and the
  last three sites came from 8 bytes of exception-handler data ahead of three
  large functions, which the analyser read as code and made a function of. Each
  has its own 8-byte entry now. Result: 0 errors and 142 source files plus
  `ppc_func_mapping.cpp`, all of which `clang++-18 -fsyntax-only` accepts with the
  runtime's flags. They have not been compiled to objects or linked: that needs
  an `mw3` block in `runtime/title.h` and in `CMakeLists.txt` (step 4).
- **Step 4, title block:** `runtime/title.h` has an MW3 block (`-DMW3_TITLE=1`),
  with the entry point (`0x82459E58`), `Com_Error`'s logging hook, the two
  kernel data-import records (`KeTimeStampBundle` at `0x820007B0` and
  `KeDebugMonitorData` at `0x8200093C`, found by their import words), and zeros
  for what is not derived. The other located hooks are listed in it, not
  enabled: they read D3D's device and the title's structures at MW2 offsets,
  which moved. 74 of the 77 sources of `runtime/` outside `gpu/` compile against
  it; the three left need FFmpeg, a generated playlist header and the title's
  hash, none of which the MW3 target supplies. `gpu/` could not be checked, as
  Vulkan and SDL headers were not available. The 51 top-level sources are now
  part of `mw3-recomp-check`.
- **Imports on the startup path** (`tools/audit_mw3_startup.py`): of 258 kernel
  imports, 188 are reachable from the entry point; 161 of those have a runtime
  implementation and 27 only a logging stub. The ones to implement first are
  `RtlImageXexHeaderField` (called in the CRT startup, `sub_82462E50`), the C
  formatters `sprintf`, `_snprintf`, `_vsnprintf` and `vswprintf` (used on the
  `D3D_Present` path among others), `KeInitializeDpc` and `KeInsertQueueDpc`
  (see MW3-DPC-INVESTIGATION.md), `VdSetDisplayModeOverride`, and
  `RtlUnicodeStringToAnsiString` with `RtlFreeAnsiString`. The network, `Xam*UI`
  and bug-check imports can stay stubs for an offline boot.

- **Gotcha:** XenonRecomp crashes with a null `FILE*` and no message when its
  output directory (`ppc_mw3/`) does not exist.

### D3D9 device offsets and the first two hooks

The two hooks that carry the frame loop, `T_D3D_Present` and `T_D3D_ArenaWait`, are enabled in the MW3 title block. Their bodies read two fields of D3D9's device structure, which moved. Both are now table entries (`T_DEV_PresentInterval`, `T_DEV_ProgressBlock`) instead of constants in `gpu/d3d_hooks.cpp`; MW2's blocks keep 13596 and 10896.

How the MW3 values were found: `sub_820A11B8` writes the flip packet (the immediates 1401 and 15360 appear in it and in MW2's `sub_820C2E60`) and has the same sequence of device accesses in the same order, every large offset shifted:

| Field | MW2 | MW3 |
|---|---|---|
| ring position (read twice around the packet) | 10900 | 11028 |
| `D3DRS_PRESENTINTERVAL` | 13596 | 13872 |
| a field read after it | 11860 | 12156 |
| a flag byte | 10941 | 11069 |
| arena progress block (first load of `sub_8209B5E8`) | 10896 | 11024 |

The shift is not uniform (+128, +276, +296), so none of these can be derived from another by adding a constant. `sub_820A16E8` takes the device in `r3` and uses 11024 and 21908 on it, consistent with the table. Not yet checked on a live boot: that the interval field is read by the flip handler the way MW2's is, and the remaining device offsets in `docs/d3d9-seam.md` (command buffer base, cursor and end), which the runtime does not read from the guest today.

### Shader preload hooks

`T_D3D_InitPixelShader` (820984F0) and `T_D3D_PatchVertexFetches` (820A4468) are enabled. The first is statement-for-statement MW2's `sub_820B8B58`. The second was found by searching both executables' generated code for the four large immediates MW2's `sub_820B6B10` uses (22413312, 3145728, -1077542912, -1077936128): each executable has exactly one such function, both are 1572 bytes, and their sequences of structure accesses are identical. The hooks only read a shader's header after D3D's own routine ran and check its magic first, falling back to compile-at-first-draw, so a wrong guess costs startup time rather than correctness. Not checked on a live boot.

`tools/find_by_immediates.py ADDR` automates that search. It ignores the high and low halves of addresses, which are placed differently in each build; an earlier version did not, and found nothing for this very hook. Checked against the known hits it finds `PatchVertexFetches` uniquely (identical access sequence) and lists `Image_FlushMove`'s location (823D4398) among three candidates, agreeing with the earlier match. On the hooks still missing it is not conclusive: `D3D_ReplayRecording` has six same-constant candidates in the D3D library with different access sequences (MW3's D3D build differs there); `Job_WaitPredicate`, `DB_MissingAsset` and `Dvar_RegisterInt` have no large immediates to search by; `CG_ViewFov` matches hundreds of functions on one constant. `CG_ViewFov`, `DB_MissingAsset`, `Job_WaitPredicate`, `Dvar_RegisterInt` and `D3D_ReplayRecording` (diagnostics only) stay unlocated; they need a structural match on call graph and data references, not constants.

### The `default.xex` relaunch is an error restart

`XamLoaderLaunchTitle` is reached through the XDK's `XLaunchNewImage` wrapper (`sub_82455AC0`, which recognizes the `XLNI_*` keywords), from three places: a dirty-disc error (`sub_82456050`), a relaunch of `default_mp.xex` with launch data (`sub_821233C8`), and `sub_8232E638`, a printf-style fatal-error function with 77 callers. That last one formats `"e%s"` into a 1000-byte global, hands it to `XamLoaderSetLaunchData` (the text starts at +4) and relaunches `default.xex`, the title's restart-to-show-the-error. The runtime now logs that text, and the CI smoke test shows `eERROR: Could not find zone 'ui.ff'`, so the handoff seen so far is a missing-file error and not a chain-load. `patch.ff`, `patch.ffm`, `ui.ffm` and `update:\\patch.ff` are also asked for before it. They are optional: the disc dump has no `patch.*` (title-update files) and no `ui.ffm`, only `ui.ff` and `ui_mp.ff`, and only `ui.ff` ended the run.

### Fastfile progress

With `ui.ff` supplied the run passes it (the 9.9 MB zone loads and 4 shaders are used) and stops on `ERROR: Could not find zone 'common.ff'` (the 39.8 MB file was then added to the private repo through Git LFS), again through the launch-data message. The startup function `sub_8229C308` names the zones it loads: `code_post_gfx` and `common` (strings at 0x820203CC and 0x820203C4), after the `ui` zone requested earlier. So the full startup set is `code_post_gfx.ff`, `ui.ff` and `common.ff`; level zones are requested later by the level loader and are not known statically. `common_specialops` and `common_survival` also exist as strings and belong to Special Ops. `common_mp.ff`, if the dump has one, does not substitute for `common.ff`; the title builds the file name from `%s.ff`.

### Past the zones: `imagefile1.pak`

With `common.ff` supplied (CI run 43387636948) the title loads its startup zones and runs: a profile signs in, 17 frames are submitted (802 draw packets, 4 shaders, 6041 command packets, no unknown opcodes, no refused loads, the graphics interrupt serviced every frame, audio callbacks 297, no crash). ### Hooks checked without game files

- `RtlRaiseException` is implemented: MW3 raises `0x406D1388` (the thread-naming convention) from its thread start-up, the only unimplemented import the smoke runs reached; the calling host thread is now named and other codes are logged.
- `T_Image_FlushMove` (823D4398) is enabled. MW2's `sub_823A52F8` and it make the same 20 calls in the same order (callees map one to one) and use destination, source and size the same way; only a device offset moved (13320 -> 14472). The hook wraps the function without reading any structure.
- `T_Memcard_InitializeSystem` (8232EC08) stays disabled. The function is MW2's shape (it clears a memcard structure, 6928 bytes against MW2's 3208, then initializes it), but the hook writes into a separate per-controller device table whose MW3 address is not known: MW2's table is not inside the cleared structure (it lies 11,392 bytes below it, at 0x83A53020) and no MW2 code builds its address directly, so it is reached through a base and an index. Its absence costs a one-time save-device prompt, not boot.
- `T_Cbuf_AddText` and `T_CG_CullZoom` are not yet checked this way.

## Title update

The disc's executable and the title-updated one differ, and the recompiled
code is for exactly one of them. MW2's build applies the update's patch with
`tools/xexpatch.cpp`. For MW3 I do not know the update's package layout or
whether it patches the executable at all. Before step 3: dump the update from
your console, run `tools/stfs.py` on it, and see what it contains. Decide
then whether to build the disc's executable (simplest) or the patched one
(matches what players have).

## PS4

Not started. The model is
[gta4-ps4](https://github.com/plastikman/gta4-ps4): an OpenOrbis build, Mesa's
RADV for Vulkan, audio and memory layers for the console, run on a jailbroken
PS4. Its README reports GTA IV at about 20-25 FPS on a PS4 Pro, CPU-bound on
the console's Jaguar cores. MW3 targets 60 FPS on the Xbox 360, so the first
question for a PS4 build is the per-frame CPU cost measured in step 5.
Two PS4 problems to investigate before anything else:
- the runtime reserves a 4 GiB address space and maps the 512 MB of guest
  physical memory at two windows ([runtime.md](runtime.md#guest-address-space));
- the GPU write-watch is built on page protection faults.

Neither is known to work on the console. gta4-ps4's `ps4/` directory is where
to look for how that port handled memory.
